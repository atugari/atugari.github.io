# 問題生成の高速化と検証記録 — 2026.11.05.100

リリース `2026.11.05.99` と高速化版を、同じ条件・同じIDで比較した。表の「300盤面」は、300個の盤面からなるマルチナンプレ1問を意味する。独立した問題を300問生成した時間ではない。

マルチナンプレでは候補計算・制約モデル構築・唯一解検査の重複処理を減らした。通常9×9の高難度では、候補の伝播と差分の巻き戻しを使う解数カウンターへ置き換えた。生成後は保存済みの一覧情報を再利用する。最終候補では通常の生成保存に必要な指紋計算を1回にまとめ、4,096マスを超える問題の圧縮と指紋計算を保存専用Workerへ移した。使用する解法、難易度の合格条件、既存のIDや保存形式は維持する。比較した正常な生成ケースでは、候補の順序と結果の一致も確認した。

集計値と測定結果は [generation-speed-20261105.json](generation-speed-20261105.json) に保存した。公開状態はこの資料では判定していない。

## 工程別の負荷

### 生成エンジン

高速化版の300個の25×25について、計測器を入れた1回の実行は合計6.399秒だった。内訳は以下のとおり。計測器の負荷があるため、前掲の生成時間と直接比較しない。

| 工程 | 所要時間 | 範囲 |
|---|---:|---|
| 配置・制約モデルの構築 | 1.354秒 | `layout`・`geometry`・`setup` の自己時間の合計 |
| 完成盤面の作成 | 0.624秒 | 重なりと各盤面のルールを満たす完成配置 |
| 論理解法による検査 | 3.026秒 | 10,635回。数字の削除中の確認と、最後の難度確認を含む |
| 最終的な唯一解検査 | 0.424秒 | 論理解法とは別の解数検査 |
| 共有マスが必要である証拠の作成 | 0.254秒 | 盤面を単独にした場合の別解の確認 |

論理解法の時間は、数字の削除判断と最後の難度判定までを完全には分離していない。旧版の同じ計測器付き実行は23.5秒という外れ値になったため、工程別の短縮率には使っていない。

Chromiumで、生成済みの300個の25×25からなる問題を使い、生成後の処理を分離した。187,201マス、プレイ用項目を含むJSONで6,327,378バイトの問題である。この試験は実生成をもう一度行った時間ではなく、同じ検証済みデータの受け取り後を測ったもの。ここでの保存はIndexedDBへの自動保存を指す。

| 処理 | 旧版の1回の測定 |
|---|---:|
| 形式・盤面の検証 | 269.7ミリ秒 |
| 重複確認用の指紋の作成 | 410.6ミリ秒 |
| 保存するレコードの圧縮・整形 | 812.7ミリ秒 |
| 保存用の一覧情報で再度行う指紋の作成 | 451.3ミリ秒 |
| IndexedDBへの非同期コミット末尾 | 35.0ミリ秒 |
| 保存後に再度行う一覧情報の作成 | 316.4ミリ秒 |
| 受け取り後の処理全体 | 2,297.7ミリ秒 |

保存改善前の初期候補では最後の一覧情報の再作成を省き、コミット済みの一覧情報を使う。この操作は同じ試験で測定分解能上0ミリ秒となり、一覧情報と指紋は旧処理の結果と完全一致した。旧処理全体の約13.8%に相当する部分を除いたことになるが、この比率を実生成込みの全体短縮率として扱わない。

この時点の初期候補には、大きな問題の圧縮と指紋計算がメインスレッド上に残っていた。続く保存改善でこの処理をWorkerへ移した。最終候補の比較は後掲する。

### 自動バックアップ

自動バックアップは生成処理とは別のタイマーで動き、長い生成中に重なる可能性がある。起動後の初回確認は8秒後、その後は15秒ごとに確認し、スナップショットの間隔は180秒。画面へ戻ったときも確認する。保存中のレコードがある場合はその保存を待ち、コミット済みの圧縮レコードを読み出す。バックアップの圧縮は既存の専用Workerで行っている。

生成の測定区間中にバックアップが実行されなかった例を、バックアップの処理時間0として扱っていない。生成とは別に、前述の187,201マスの検証済み問題1問を使って自動バックアップを測定した。

| バックアップの測定範囲 | 所要時間 |
|---|---:|
| 保存済み圧縮レコードの読み出し・スナップショットの準備 | 53.7ミリ秒 |
| ローカルのバックアップ作成全体 | 1,444.1ミリ秒 |
| Worker作成から結果が届くまで | 1,363.1ミリ秒 |

Workerの値には起動とデータの受け渡しも含むため、圧縮だけの時間ではない。圧縮前のスナップショットJSONは4,426,625バイト、保存されたバックアップ本体は848,016バイトだった。読み戻したID・問題・解答は一致した。このバックアップ試験ではメインスレッドの長時間処理と応答間隔を採取しておらず、0件や停止なしとは判定していない。バックアップ方式自体は今回変更していない。

## 継続作業での保存処理改善（最終候補）

通常の生成保存では、重複確認と保存用一覧の指紋を一度だけ計算する。4,096マスを超える問題は呼出し時のJSONを確定し、保存専用Workerで従来と同じ圧縮とSHA-256を行う。Workerが利用できない場合は同じJSONを使う従来処理に戻る。通常の編集保存やバックアップの形式は変えていない。

準備済みデータは保存内部に保持し、同じ書込キュー内で重複を判定する。重複時には問題も生成進捗も追加しない。保存失敗時にはその生成問題の未保存印だけを取り除き、以前から未保存の編集は保持する。これにより、保存失敗後の再開で次の保存成功まで失敗と誤判定する不具合も修正した。
