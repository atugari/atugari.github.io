# 端末ごとの自動登録と移行のローカル検査

本体の `RefillStore.java` と `RefillBootstrap.java` を改変せずコンパイルし、format 2 の同じ自動登録設定を複数端末へ配った場合の登録・移行・失敗からの復旧を検査します。接続先・登録キー・旧 token は架空の値だけを使用し、ネットワーク、管理者キー、本番 API、署名鍵は使いません。

## 実行

Python 3、JDK 17、Gson JARが必要です（Gson 2.10で確認）。アプリのディレクトリで実行する例：

```sh
python3 tests/bootstrap/run.py \
  --jdk /path/to/jdk-17 \
  --gson /path/to/gson-2.10.jar \
  --out /tmp/refill-bootstrap-results.json
```

`--jdk` は `JAVA_HOME`、`--gson` は `GSON_JAR` でも指定できます。`--app` は検査対象アプリのディレクトリを変更するときに使います。既定値はこの `tests/` の親なので、実行時のカレントディレクトリには依存しません。`--out` を省略すると結果JSONを標準出力に出します。コンパイル先は一時ディレクトリで、実行後に削除します。

## 検査の範囲

主な検査対象は次のとおりです。

- 同じ設定でも各端末が別の token を生成し、再起動・再試行では同じ token を使うこと。
- 旧共有 token のハッシュが厳密に一致する登録だけを移行し、手動登録・別接続先・解除済み端末を変更しないこと。
- 移行中も利用者の性能・通信・在庫・自動補充設定と集計値を保持すること。
- `commit()` がメモリを更新した後に失敗しても、登録完了扱いにせず、HTTP の前に同じ候補を永続化すること。
- サーバー受理後の応答消失や完了保存失敗を、同じ端末登録で再試行できること。
- 通信断の後でプロセスを再起動しても、次の起動で同じ候補を再試行し、旧共有 token で補充を始めないこと。解除後の古い再試行要求は HTTP を送らないこと。
- 同時起動・同時完了・通信中の解除・手動登録に対して古い応答が上書きしないこと。
- 旧 SharedPreferences の送信待ち情報が残る間は登録を完了せず、旧 job / lease を新 token に渡さないこと。
- 移行中・移行後の古い status / 403 応答が、新登録の表示や自動補充設定を変えないこと。
- 不正設定・想定外フィールド・過大な asset と、asset 読み込み失敗を処理できること。

Android の SharedPreferences と AssetManager は模擬実装です。保存済み状態とプロセス内の状態を分け、保存失敗時にもメモリは更新される挙動を再現します。JSON は Gson を使う最小 adapter で、Android の JSON パーサー自体の互換性試験ではありません。`RefillRunner` はロック境界だけのテスト用 adapter に置き換え、HTTP が完了保存用ロックの外にあることを検査します。

実機へのインストール、Android 上の画面操作・JobScheduler・Service のライフサイクル、本番サーバーの認可や登録上限は検査しません。別端末・別 applicationId の検査は分離した Context を与えるもので、Android OS のアプリ分離自体を検証するものではありません。旧盤面の SQLite 保存と配送所有者の解除は、別の `tests/multi-registration/run-vault.py` で実際の SQLite を使って検査します。

本体ソースの SHA-256 を結果に記録し、実行中に本体が変更された場合は失敗します。Java のコンパイルと実行には、それぞれ 60 秒の上限があります。
