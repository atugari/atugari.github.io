# ナンプレ補充係 Android 試作版

0.2.3のソース更新では、通常9×9、とくにLv18の生成で繰り返す唯一解判定を高速化した。
候補の作り方、難易度の採用条件、完成後の証明検査は変更しない。
最大性能モードの複数Workerでも、それぞれが高速化した判定を使う。
配布済みAPKは0.2.2。0.2.3のAPKは、元の署名鍵による署名とAndroidでの確認が済んでいないため未配布。
測定条件と結果は [0.2.3の高速化記録](../../docs/nanpure/refill-speed-20261105.md) を参照。

ナンプレの未出題在庫を補充する管理者用アプリ。生成はスマホ内で行う。PCや同じWi-Fiへの接続は不要。

1. 自販機の管理画面で端末登録リンクを発行する。
2. Xperiaで登録リンクを開き、「このスマホを登録する」を押す。試験サーバーの接続先は初期設定済みで、登録コードはリンクから入る。
3. スマホを電源と許可した回線につなぐ。従量制回線の利用は初期状態で無効。
4. アプリの「連続補充を今すぐ始める」を押す。電源と回線の条件を満たしていれば、その場で仕事を確認する。
5. スマホにも問題を貯める場合は「端末在庫を作る（オフ）」を押し、条件ごとの目標を設定する。入力欄の初期値は各10問。0問を設定すると自動で作り置きする動作を止める。
6. CPUを広く使う場合は、設定の「連続補充で最大性能を使う」をオンにして連続補充を始める。予約は同じ条件を複数のWorkerで探索して最初の完成品を使う。すぐに作れる通常ルールのLv.1〜3の予約は1並列で、端末在庫は不足条件を並行して生成する。

試験用のサーバーを使う場合は、登録する前に「接続先を設定」でHTTPSの接続先を指定する。端末の登録権限は登録時の接続先に固定される。登録用QRが設定するのはコードだけ。

連続補充は、通知を伴うAndroidのフォアグラウンドサービスで動く。外部電源につながっていれば、バッテリーの充電が一時停止していても動作する。棚に空きがない間は約1分おきに確認し、画面オフでCPUを起こすのは探索中だけ。電源・許可した通信・温度の条件を外れた場合は連続補充を終了する。「連続補充を停止する」は、アプリ画面と通知の両方にある。通知を許可しなかった場合はアプリ画面から停止できる。

「充電中に自動で補充する」がオンなら、連続補充の終了後もAndroidのJobSchedulerで定期的に補充を確認する。充電や回線、OSの状態で開始は遅れることがある。どちらの方法も止める場合は、連続補充を止めて自動補充をオフにする。画面を消した状態での稼働は、機種ごとに実機で確認する。

最大性能の並列数は、Androidがアプリに提供するCPU数とメモリの空き、端末温度に応じて決める。探索中の温度上昇では並列数を下げる。自動補充は1並列で動作する。完成した盤面は1問ずつアプリに渡し、保存と送信は順番に行う。

生成は75秒を上限の目安とする区切りで実行する。探索に終了を通知してから強制停止までに猶予を設ける。100×100の検証済み小盤面候補は、探索が自分で終了して同じWorkerが動き続ける場合に次の探索へ引き継ぐ。端末在庫は固定の23ルール・427条件を対象に、在庫の少ない条件を順番に回す。回線が切れていても、電源と温度の条件を満たす間は手動の連続補充で作り置きできる。

完成品はSQLiteへ圧縮保存し、条件別の件数と取り出しには索引と集計を使う。データベースと作業領域に32GBの上限を設け、端末の空きが約8GBに近づくと新規保存を停止する。登録情報や受理待ちの完成品は上書き更新で引き継ぐ。受理確認が届くまで完成品を保持し、再送時は割り当てとIDを再利用する。

全条件を有効にした試験サーバーでは、固定の23ルール・427条件の完成品を0.2.0から補充できる。サイトはサーバー在庫が足りない条件の予約も受け付ける。

## ビルド

- Android 8.0 以上、ビルド用 Android SDK 35。
- JDK 17、Gradle 8.7以上、Node.js。
- リポジトリのルートから `cd android/nanpure-vending-worker` に移動し、`gradle assembleDebug` を実行する。
- 生成エンジンの基盤はリポジトリ内の公開リリース 2026.11.04.95 からビルド時に取り出す。通常9×9の唯一解判定には `engine-overrides/unique-solver.js` を組み込む。候補生成、難易度判定、証明の再検証は基盤のものを使う。
- この判定処理は公開版 2026.11.05.100（commit `cc0068e47e68e15474a65de27eb9a7ae9eb01d00`）の `notebook/unique-solver.js` と同じ内容。既存427条件のキーと保存形式は変更しない。
- エミュレーターでローカルAPIを使う場合は、ビルド時の `NANPURE_REFILL_ENDPOINT` に `http://10.0.2.2:ポート/api/vending/worker` を指定する。
- 組み込みエンジンの軽い検査は `node test-engine.cjs` で実行する。
- 高速化した判定の独立検査と条件定義の一致確認は `node test-unique-solver.cjs` で実行する。

試作APKを使うには、自販機の補充APIと端末登録コードが必要。既存の生成補助の登録コードとは別。

## 上書き更新の署名

配布済み0.2.2の証明書SHA-256は
`6FFC4CA915A22C1C0B46DDAECA5FE472FC4E28875AA313A1149ABE21094ACE3C`。
登録情報と端末在庫を保ったまま上書き更新する配布APKは、この証明書に対応する元の秘密鍵で署名する。
`assembleDebug` が新しく作る鍵は代用できない。元の鍵を復元できるまで更新用APKの配布を完了扱いにしない。
秘密鍵は公開リポジトリに置かず、制作更新用の非公開バックアップに保管する。
